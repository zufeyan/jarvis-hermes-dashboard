# Native Hermes approval transport and restricted HUD contract

**Status: investigation only.** This document proposes an integration boundary; it does not claim that the dashboard currently has an approval endpoint, nor that generic tool-side effects are currently mediated by approval. No implementation/config/runtime changes are authorized by this review.

## Finding: there is source-supported transport, but it is approval for dangerous commands

The native CLI approval transport is the closest reusable mechanism. It is **not** a generic “approve every tool before execution” RPC.

- `~/.hermes/hermes-agent/hermes_cli/approval_transport.py:31-53` defines immutable `ApprovalRequest` / `ApprovalDecision`: request ID, digest, redacted command/description, pattern key(s), surface, timeout, and allowed choices. `:55-78` builds a random request ID and SHA-256 digest over canonical JSON including the session key; decisions echo request ID + digest.
- `.../tools/approval_prompt.py:199-206` says selected transport replaces built-in prompt surfaces while detection, allowed scopes, persistence, timeout, and final authorization remain host-owned. `:221-253` redacts command/description, creates request, emits hooks, invokes transport, and records outcome. `:256-277` denies transport failure unless explicit builtin fallback is configured; never fallback implicitly.
- `.../hermes_cli/plugins.py:430-453` is the registration interface; `:1451-1472` enforces unique names and retrieval. A plugin transport is inactive absent explicit selection (`tools/approval_prompt.py:207-219`). Do not enable or alter global config as part of this proposal.
- `.../hermes_cli/approval_transport.py:103-185` runs bounded workers (max 8; `:24-25`), times out, fails closed, discards late results, and validates decision type, request ID, digest, and allowed choice. It does **not** expose an HTTP route or persistent pending-request store; the plugin callback itself must bridge to its UI safely.
- `.../acp_adapter/permissions.py:15-21,33-51,54-64` uses stable ACP permission option IDs (`allow_once`, `allow_session`, `allow_always`, `deny`, optionally `deny_always`) and unique `perm-check-N` tool-call IDs. `:77-114` schedules `request_permission`, waits with timeout, cancels the future on timeout/failure, and closes the pending UI bubble. `:128-153` maps only known option IDs and otherwise denies. These are ACP permission IDs, distinct from the host transport's random request ID/digest.
- `.../acp_adapter/server.py:616-641` exposes native ACP new/load/resume session methods; `:643-664` implements cancel by setting the session cancel event, hard-interrupting the agent, and interrupting session delegations. `:818` is the ACP prompt handler. This is an ACP protocol implementation, not a documented local HTTP API for the HUD. Do not invent URLs by translating ACP method names.

## Scope boundary: terminal gate vs generic hooks

The approval transport is reached by `tools/approval_prompt.py` through the dangerous-command approval flow. ACP bridges that callback at `acp_adapter/server.py:929-934`; `acp_adapter/permissions.py:128-153` documents the callback as used by `tools.approval.prompt_dangerous_approval()`. This supports **classified dangerous terminal commands**, not all tool calls or every external side effect.

`hermes_cli/plugins.py:110` lists `pre_tool_call` as a tool hook; `:1971-2048` resolves its directive and `:2083-2088` dispatches it as a hook. The hook can veto/block a tool call, but the source describes it as a hook—not a host-owned permission RPC with per-action request/digest, approval scopes, timeout/decision validation, and generic mediation. It is not sufficient to claim universal approvals. ACP cancellation (`server.py:643-664`) is native session cancellation, separate from approval decision and unrelated to a hypothetical dashboard cancel route.

## Current dashboard evidence and non-claim

The project's `server.py:1,19,75-98,100-148` is explicitly loopback voice-only and has agent/tool execution disabled. `:143-148` returns inert responses for `/api/new` and `/api/cancel`, 503 for `/api/run` and `/api/jobs`; none is a native Hermes API. `runtime.py:290` raises `RuntimeError("agent execution disabled pending verified approval integration")`. Thus no live dashboard-run/poll/approval contract exists to reuse today.

## Minimal proposed HTTP + frontend contract (not existing routes)

Keep the loopback server, same Hermes provider/default agent/config, and route work through an in-process host integration using the existing transport semantics. The following are **proposed resource operations**, not claimed native endpoint names; choose concrete route strings only during implementation and document them there.

1. **Start run:** client sends user prompt + an opaque `client_request_id`; server creates/binds a Hermes session and run ID, returns run/session IDs, state, and a monotonically increasing event cursor. Reject duplicate client request IDs idempotently. Do not accept client-selected tools, provider, agent, approval mode, or filesystem scope.
2. **Poll:** read-only status/events for a run using cursor; return assistant text/status and pending approval display data only. Approval object mirrors redacted immutable request fields (`schema_version`, request ID, digest, command/description, pattern keys, surface, expiry/deadline, allowed choices). Never expose secrets or treat client display text as authority.
3. **Decide:** submit exact `request_id`, `digest`, choice from the server-provided `allowed_choices`, and a one-use decision idempotency key. Server verifies ownership by authenticated run/session binding, pending state, deadline, exact digest, allowed choice, and not previously consumed; atomically consume before resume. A timeout, stale/mismatched digest, duplicate/replayed decision, unknown choice, lost run, or internal error resolves to deny. Use `once` only for pilot; do not expose session/always unless host policy explicitly permits them.
4. **Cancel:** server-side interrupt of that run's native Hermes session and its delegated work; mark all pending approvals denied/invalidated, reject later decisions, and acknowledge actual terminal/interrupted state rather than returning a decorative `{ok:true}`. ACP implementation at `acp_adapter/server.py:643-664` is evidence for native cancellation mechanics, not proof an HTTP wrapper exists.
5. **New:** create a fresh Hermes session via the same runtime; do not equate “new conversation” with cancellation of an existing run. Explicitly preserve the configured provider/agent defaults; avoid changing global config.

Use exact expiry: host monotonic deadline governs; UI countdown is advisory. On expiration invalidate request and fail closed. A late approval can never authorize a later action. Keep one pending approval per action, not one global mutable “current approval” slot. Use unique request IDs and per-run ownership, serialize each run's decisions atomically, and ensure concurrent approvals cannot overwrite each other (the CLI code itself serializes its built-in modal at `cli_modal_mixin.py:1063-1072`; transport requests are separately correlated by IDs/digests). Multiple tabs may observe the same run read-only, but only the run owner (a server-issued, unguessable, HttpOnly/SameSite session capability or equivalent) can decide/cancel. Bind CSRF/origin checks to existing protections; do not put owner tokens in URLs/local storage/logs. Losing the owner must not silently transfer authority; permit explicit re-claim only via a designed user gesture and invalidate old lease. Tabs must not each auto-submit decisions.

## Fail-closed pilot boundary and bypass review

Until every applicable route is host-mediated, do **not** expose general agent/tool execution in the dashboard. Keep `/api/run` disabled (current 503), preserve actual provider + agent defaults unchanged, and do not claim “no tools” unless the runtime tool list and every execution route are verified. A UI-only confirmation, prompt instruction, or `pre_tool_call` hook is not a security boundary.

Before enabling any pilot, explicitly inventory and block or mediate these routes, each with server-side policy—not just frontend hiding:

- **Commands / terminal:** shell and bang-shell, command aliases/slash commands, subprocesses, scripts and shell chains. Existing dangerous-command approval classifies terminal commands only; safe-looking commands can still have side effects. `approval_transport.py` does not promise all shell commands are individually approved.
- **Background / delegation:** subagents, async delegation, detached tasks and background review can execute after the initiating response or in separate workers. ACP cancel explicitly interrupts session delegations (`acp_adapter/server.py:657-661`), but this does not imply all transports/workers are universally covered. Disallow delegation for restricted pilot until cancellation/approval propagation is proven end-to-end.
- **Browser / network / email:** browser automation, HTTP/API/MCP tools, mail send, messaging and other external integrations can mutate remote state without terminal approval. Explicitly disable these tools and any user-installed MCP/plugin surface in pilot; a generic pre-tool hook that can be skipped, fail open, or miss delegated calls is inadequate.
- **Filesystem / code writing:** `write_file`, patch, code-edit tools, upload/delete and similar tools can change data outside terminal's command classifier. Disable them for a read-only pilot or add host-owned per-action mediation covering every tool executor and worker; confirmation must bind exact operation/path/content digest and target, not mere natural-language intent.
- **Approval bypass/config:** prevent `/yolo`, CLI `--yolo`, `approvals.mode=off`, approval allowlist/session/permanent grants, alternate clients/transports, and direct access to Hermes runtime outside the guarded HUD. Keep transport fallback unset (transport source only falls back to builtin on explicit `transport_fallback: builtin`, `tools/approval_prompt.py:256-277`). No change to global config was made or should be inferred.

Minimum restricted-pilot allowlist: plain text conversation only with a server-defined minimal tool list verified empty or strictly read-only; no terminal, file write, browser, email, external side-effect, plugin/MCP, background/subagent tools. If that allowlist cannot be enforced in the actual Hermes runtime—not just by prompt—remain voice-only with `/api/run` returning 503. Approval of dangerous shell commands alone is insufficient to graduate the pilot.
